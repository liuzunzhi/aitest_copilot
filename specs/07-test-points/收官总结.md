## 3. 数据模型

### 3.1 两张新表

- **`test_point_analyses`（生成记录）**：模板与版本快照、provider、依据的增量分析与基线快照、
  `status`（pending / running / succeeded / failed）、`error_code`、`stats`、起止时间。
  与 05 的分析记录同构——一次生成是一条可追溯的任务。
- **`test_points`（测试点）**：名称、目标（`target_type` + `target_id` + `target_name` 快照）、
  优先级、前置条件、验证要点、章节快照、来源标签 / 来源结论、评审状态与意见、
  `needs_review` 三列、`source_type`（llm / manual）。

**关键决策**：

- **不建唯一键**：同名测试点合法（不同功能可以有同名测试点），只靠 `idx_tpoints_target` 检索。
- **`target_name` / `chapter_title` 落库快照**：目标后来改名或被删，历史测试点仍对得上原文。
- **`analysis_id` 可空**：手工新增没有来源生成记录。
- **生成记录与测试点分表**：生成是一次性任务，测试点有独立评审生命周期，还会被 08 期引用。

### 3.2 迁移 `0022`

- `down_revision = "0021"`；按外键顺序建表，`downgrade` 反序直接删表（规避 MySQL 1553）。
- `llm_run_logs.task_type` 的 CHECK **先删后加**（MySQL 不支持直接改 CHECK）；
  三层验证：约束文本含 `'test_point'`、实插成功、插 `'bogus'` 被拒（3819）。
- 播种 1 条 active 模板，`system_prompt` / `user_prompt` 各带 Mock 前缀；
  **JSON 示例的 `target_id` 写 `123`**——真实模型会照抄示例值。

## 4. 架构与关键设计

### 4.1 输入口径（本期只做一条路）

| 输入 | 口径 |
|---|---|
| 基线标签 | 一律 `baseline_labels.status='active'`，复用 04 的判定，不另写一套 |
| 结构实体 | 复用 04 的 `approved_entities()`，不自己判断「哪些节点算生效」 |
| 增量结论 | 只吃**未全部撤销**的分析记录；全部撤销 → 400 `TEST_POINT_INPUT_EMPTY` |
| 空输入 | 标签与结论都没有 → **400 拒绝发起**，不生成无法追溯的测试点 |

「无基线直接对文档分析」是 PRD 2.4.4 的输入②，本期明确不做（见 §8 Backlog）。

### 4.2 Prompt 五段式（可复现）

1. `template.user_prompt`（原样取库）
2. `## 可对照的基线目标` —— 模型必须知道能往哪些 `target_id` 写
3. `## 标签依据`
4. `## 增量结论`
5. `## 章节：{title}` + 正文

截断只截**章节正文**，前缀段落不动；清单截断追加「其余 N 项已省略」。
> 第 2 段是 06 期 L2 联调的血泪教训：不给清单，模型只能瞎猜 id。

### 4.3 模型输出校验（不猜、不修）

| 情况 | 处理 |
|---|---|
| `test_points` 不是数组 / 坏 JSON | 整次失败（复用 `parse_llm_json`） |
| 缺 `name` | 整条丢弃，计入 `stats.discarded` |
| `target_type` 非法 | 整条丢弃 |
| `target_id` 不在本次依据清单内 | 整条丢弃（`TEST_POINT_TARGET_OUT_OF_BASELINE`） |
| `priority` 非法 | **归一到 `medium`**，不丢 |
| `precondition` / `verification` 缺失 | 存空串，不丢 |

### 4.4 待复核标记（不改内容）

标签被清除时，04 的 `clear_label()` 在成功后只做一件事：
把引用该标签的测试点置 `needs_review=1` + 原因 + 时间，**内容一个字节都不动**。
表探测保护（`_table_exists`）确保 07 迁移前后 04 的既有测试都能跑。

### 4.5 前端交互

- 生成记录表：状态、模板、文档、统计（测试点 / 丢弃 / 章节）、删除。
- 测试点表：名称（含「待复核」标记）、目标、优先级、章节、状态、来源、操作。
- 详情抽屉：全文 + 来源追溯 + 通过 / 驳回（评审限项目管理员）。
- **冲突二次确认**：所选章节已有评审通过的测试点时，前端 `modal.confirm`
  「将覆盖已有评审结果」，服务端不静默覆盖。

## 9. 踩坑与修复

| 坑 | 处理 |
|---|---|
| MySQL CHECK 违约抛 3819（`OperationalError`），不是 1062 | 断言分开写 |

| Pydantic 静默丢未知字段 | `extra='allow'` + 服务层拦截只允许 4 个可改字段 |
| e2e 清理漏 `llm_run_logs`，导致 `0022` 降级被 `test_point` 留痕挡住 | 清理清单补按 `project_id` 删除；先修现场再跑两轮往返 |
| `InputNumber` 的 `data-testid` 落在 rc-input-number 外层 | e2e 改用表单项下的 `input` |
| Mock 的占位 `target_id=123` 必然越界 → 生成 0 条 | e2e 用 `seed_test_points()` 按真实表结构补数，评审仍走真实接口 |
