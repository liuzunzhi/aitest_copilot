## 1. 一句话结论

「章节引用图」从「**AI 分析完直接落库**」升级为

## 3. 关键设计（5 条）

### 3.1 【核心裁决】待评审用 `status` 列，不复用 `source`

这是本期最重要的一个决定，也是用户点名要回答的问题。

`source` 与「待评审」在语义上**正交**：

| 维度 | 回答的问题 | 取值 |
|---|---|---|
| `source` | 这条边**是谁产生的**？ | `rule`（正则）/ `manual`（人工）/ `ai`（大模型） |
| `status` | 这条边**人认可了没**？ | `pending`（待评审）/ `approved`（已生效） |

**硬塞进 `source` 会炸四处**：

1. **幂等逻辑会吃掉已采纳的边。** 12 期的口径是「删 `(version_id, source='ai')` 再插」。
   若用 `source='ai_pending'`，重新分析就只删待评审那批——
   **用户刚点完采纳的边凭空消失**，人工评审的成果被一次重跑清零。
2. **「谁产生的」这个信息会丢。** 采纳一条 AI 边后它仍是 AI 产出的
   （`confidence` / `rationale` 来自模型），改写成 `manual` 就毁了可解释性的基础。
3. **下游过滤要写白名单。** 传播逻辑得写成 `source IN ('rule','manual','ai_approved')`，
   每加一个来源都要记得补进去，**漏一个就静默少传播一条边**。
4. **迁移成本一分都省不下来。** 唯一键 `uk_chlinks_to_chapter` 是
   `(version_id, from, link_type, to)`，**既不含 `source` 也不含 `status`**。

结论：**加 `status` 列，`source` 一个字节不改。**

### 3.2 「生效」有确切定义——能参与图传播

在本仓库里，章节引用边**只有一个下游消费者**：05 期第二遍的
`second_pass.build_point_index` 读引用图做「图传播」，沿 `references` / `depends_on`
跳一跳，把源章节的 `changed` / `affected` 结论传播成 `possible_impact` 冲突。

所以：

```python
# app/incremental/second_pass.py::build_point_index
.where(
    DocumentChapterLink.version_id == analysis.document_version_id,
    DocumentChapterLink.link_type.in_(_PROPAGATION_LINK_TYPES),
    DocumentChapterLink.to_chapter_id.is_not(None),
    DocumentChapterLink.status == "approved",   # ← 本期唯一新增的条件
)
```

**只加这一个条件**，算法、错误码、`_PROPAGATION_LINK_TYPES` 全不动。

> 不加它，「待评审」就只是前端的一个分区标签，语义上等于没做。
> AC-231 专门验证：`pending` 边**不产生** `possible_impact`，改成 `approved` 后**产生**。

### 3.3 重新分析不冲掉已采纳的边

12 期口径是「删所有 `source='ai'` 再插」。本期改成：

```
1. 只删 (version_id, source='ai', status='pending') 的旧行
2. 插入新的 AI 边，status='pending'
3. status='approved' 的 AI 边原样保留
```

同时，新分析出的边**命中任何已存在的同一条边**（不论来源、不论状态）就**跳过**——
因为唯一键不含 `source` / `status`，不跳过会撞键 500。

> 这是「人工评审不被重跑清零」的保证（AC-232）。

### 3.4 采纳幂等 + 批量原子

| 场景 | 行为 | 理由 |
|---|---|---|
| 已生效的边再采纳 | **200**（幂等），且**不写审计** | 本期无驳回态，`pending → approved` 是唯一迁移，「再确认一次」语义成立；审计记业务变更，没变更不该有记录 |
| 批量含不存在的 id | **整批 404**，一条都不改 | 「部分成功」会让用户不知道哪些进了 |
| 批量空数组 | **400** `INVALID_CHAPTER_LINK` | 复用既有错误码，**本期零新增** |

> 与 07 期「已评审过就 409」不同：那里的评审有**决策语义**（通过 / 驳回），
> 重复「通过」确实矛盾。本期没有驳回，不存在这个问题。

### 3.5 前端三区 + 状态驱动 + 锁屏

```
┌─ 章节引用图 ────────────────────── [✨ AI 一键分析引用] ─┐
│  Alert（三态：空数据 / 有待评审 / 只剩已生效）            │
│  【待评审区】全选 + 已选 N 条 + 批量采纳 + 清空           │
│  【已生效区】                                            │
│  【补一条引用关系】                                      │
└──────────────────────────────────────────────────────────┘
```

- **提示语三态**：12 期原文案**一字不改**，只从「永远显示」变成「条件显示」
  （只在「无待评审 + 有已生效边」时出现）。
- **锁屏**：`<ConfigProvider componentDisabled={analyzing}>` 包住抽屉内容，
  33 个 antd 组件自动禁用；**AI 按钮必须放在 Provider 外面**，否则自己点不动。
- **详情**：每行「详情」→ 弹窗展示理由与置信度。`rationale` 是本期新增的列
  （12 期引擎已解析出理由，但**没落库**，表里也没有这一列）。

## 4. 数据模型与迁移

### 4.1 两个新列（同一张表，不新建表）

| 列 | 类型 | 语义 |
|---|---|---|
| `status` | `VARCHAR(16) NOT NULL DEFAULT 'approved'` | `pending` 待评审 / `approved` 已生效 |
| `rationale` | `VARCHAR(1000) NULL` | AI 分析理由（详情弹窗） |

`ck_chlinks_status CHECK (status IN ('pending','approved'))`——**刻意只有两值**，
不做 `rejected`（用户原话「错的直接删除」，删除写审计，历史可追）。

列、索引、唯一键、`ck_chlinks_source` **一个不动**。

### 4.2 迁移 `0028` 的四步 / 三步

```python
def upgrade():
    # ① 加可空列 + server_default —— 存量行被回填成 'approved'
    op.add_column(..., sa.Column("status", sa.String(16), nullable=True,
                                 server_default=sa.text("'approved'")))
    # ② 加 rationale
    op.add_column(..., sa.Column("rationale", sa.String(1000), nullable=True))
    # ③ 加 CHECK
    op.create_check_constraint("ck_chlinks_status", ..., "status IN ('pending','approved')")
    # ④ 收紧非空（此时已无 NULL）
    op.alter_column(..., "status", existing_type=sa.String(16), nullable=False, ...)

def downgrade():
    # ① 先删 pending 行（它们是本期独有的语义）
    op.execute(sa.text("DELETE FROM document_chapter_links WHERE status = 'pending'"))
    # ② 删 CHECK
    # ③ 删两列
```

**为什么不能一步加 NOT NULL 列**：MySQL 上把列改成 NOT NULL 时若有 NULL 行会报 1138。
必须「先加可空 → server_default 回填 → 再收紧」。

**为什么存量行回填 `approved`**：12 期已落库的 AI 边、05 期的规则边与人工边
**本来就是生效边**，加个列不该让它们倒退成待评审。

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `.../links` | 成员 | **扩 2 字段**：`status` / `rationale` |
| POST | `.../links` | 管理员 | 人工补链，落库即 `approved` |

| DELETE | `.../links/{id}` | 管理员 | 删一条（三种来源都可删） |

**错误码零新增**：采纳幂等，复用 `CHAPTER_LINK_NOT_FOUND`（404）/
`INVALID_CHAPTER_LINK`（400）。不为「将来加驳回」预留死代码——
错误码要在 `client.ts` 配中文文案，定义了却永远不抛就是白占一个位置。

**批量入参刻意不加 `min_length=1`**：空数组要让服务层抛 400，
加了 pydantic 约束会变成 422，与 spec 冲突。

## 11. 踩坑（6 个）

1. **MySQL 的 `op.alter_column` 必须显式给 `existing_type`**——
   不写会报 `All MySQL CHANGE/MODIFY COLUMN operations require the existing type`，
   而且**此时前 3 步已经落库**（MySQL DDL 非事务，不回滚），
   库停在「列和 CHECK 都在、版本号没升」的半成品状态，必须手工清理后重跑。

2. **一个文档只能有一个 `active` 版本**（`uk_versions_active`）——
   测「跨版本采纳」时构造第二个版本必须用 `pending`，用 `active` 直接撞唯一键 1062。

3. **`ConfigProvider componentDisabled` 会禁掉内部所有组件**——
   包括**触发它的那个按钮**。AI 按钮必须放在 Provider 外面，否则进去 loading 后自己点不动。

4. **e2e 抓「分析中」态要把请求挂起**——
   Mock 分析几毫秒就返回，直接点根本抓不到中间态。
   用 `page.route("**/links/analyze", lambda route: None)` 让请求保持 pending。

5. **05 期的 e2e 也在用同一个 testid**——
   `test_incremental_second_pass_ui.py::test_ac_86` 也定位 `chapter-link-table`，
   表格拆分后同样失效。**计划里只提到 12 期那个文件，实跑才发现**。

6. **开发库有历史脏数据**——
   `project_applications` 里有一条 2026-11-26 遗留的 pending 申请
   （admin 对测试项目的「申请加入」），让 02 期 3 条既有用例永久红。
   已清理并登记（删的是 pending 申请行，非业务数据）。
