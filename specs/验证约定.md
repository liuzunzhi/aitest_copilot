## 2. 任务完成定义（Definition of Done）

一个任务只有同时满足以下五条才算完成：

0. **开跑前环境自检通过**：`.\.venv\Scripts\python.exe scripts\dev_check.py`
   （跑前台用例时加 `--expect-db e2e`；用 `scripts/run_e2e.py` 会自动做这一步），
   任一 `[FAIL]` 先修环境再动代码。
1. 该任务的 pytest 用例通过（`-k ac_XX`）。
2. 全量 `.\.venv\Scripts\python.exe -m pytest` 通过，数量只增不减。
   全量加 `-n auto` 走 xdist 并行（468 条约 50s，串行 168s）；排查偶发失败时改回串行跑。
3. **Playwright 前台核对通过**（前端可用时强制执行；不可用时在提交信息与 `tasks.md` 中标注「前台待补」）。
4. 截图证据落在仓库根目录 `.screenshots/<任务号>/`，文件名含 AC 编号。

## 4. Playwright 工程约定

### 4.1 工程结构与执行方式

- 工程位置：`D:\aitest_copilot\tests\e2e\`（pytest-playwright），不再另建 Node e2e 工程。

- **默认不随全量 pytest 执行**：`pyproject.toml` 的 `addopts` 为 `-m 'not e2e'`；前台用例统一打 `@pytest.mark.e2e`。

- 执行方式：常规直接用 `scripts/run_e2e.py`，它把起服务、自检、跑用例、收尾串成一步。

- 造数：`tests/e2e/support.py` 直连 e2e 库建用户，项目/成员/申请走真实 API；UI 只负责被验证的那一步。

### 4.2 用例命名与断言

- 用例命名 `test_ac_XX_<场景>_ui`，与 spec 的 AC 编号一一对应。

- 每个用例至少断言：页面可见文案 / 列表条数 / 关键按钮状态之一，不只看「没报错」。

- 失败自动截图 + 保留 trace；成功也保留 1 张关键帧（`shot` 夹具）。

- 登录态复用：`admin_storage_state` session 级 fixture 登录一次并复用 localStorage。

### 4.3 选择器与组件拆分约定

- **选择器约定**：前端新增/改动的交互元素统一带 `data-testid`（命名 `区域-动作-目标`，如 `tree-label-btn-12`、`snapshot-approve-btn`），e2e 优先 `get_by_test_id`。

- antd 内部类名（`.ant-tree-switcher_close`、`.ant-modal:visible`、`.ant-select-dropdown`）只作兜底，且必须限定在可见容器内——这些类名在升级后会变，T65 已在 `.ant-switcher_closed`、双弹窗 `.last` 上踩过。

- **组件拆分阈值**：单页组件超过约 400 行、或同时含 3 类以上弹窗/表格时拆子组件，避免一个文件里定位与回归成本过高。

### 4.4 失败处理与回归

- **失败一次收齐**：一次跑完全部失败用例，集中读报错后批量修；修完先 `-k` 收窄验证，最后再跑一次全量。不要「改一行 → 重跑全量」逐条试，那是 T56–T65 耗时最大的原因。

- **增量修改与范围控制**：拆分或重构组件时，禁止擅自将未被本次任务覆盖的组件一并拆分（如 T65 拆分基线树时越界拆分快照页，已回退）。父组件超过 400 行时，优先拆分纯渲染子组件或常量，状态与事件编排尽量保留在主文件内。

### 4.5 AI 辅助开发提效约定

- **拒绝全量投喂**：对话开始时，禁止读取全量代码库。只允许 `@` 本次任务相关的核心文件。

- **先计划，后代码**：每个 Task 必须先输出「修改计划」，用户确认后再写代码。

- **局部验证优先**：写完代码后，先执行 `pytest -k ac_XX -n auto`，不要直接跑全量。

- **长任务断点**：如果单个 Task 涉及 3 个文件以上的新增/修改，必须拆分为多个对话回合，避免单次上下文过载。

- **复用 dev_check**：修改代码前先确认 `scripts/dev_check.py` 正常，防止环境假错导致 AI 盲目排查。
