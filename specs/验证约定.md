## 2. 任务完成定义（Definition of Done）

一个任务只有同时满足以下五条才算完成：

0. **开跑前环境自检通过**：`.\.venv\Scripts\python.exe scripts\dev_check.py`
   （跑前台用例时加 `--expect-db e2e`；用 `scripts/run_e2e.py` 会自动做这一步），
   任一 `[FAIL]` 先修环境再动代码。
1. 该任务的 pytest 用例通过（`-k ac_XX`）。
2. 全量 `.\.venv\Scripts\python.exe -m pytest` 通过，数量只增不减。
   全量加 `-n auto` 走 xdist 并行（468 条约 50s，串行 168s）；排查偶发失败时改回串行跑。
3. **Playwright 前台核对通过**（前端可用时强制执行；不可用时在提交信息与 `tasks.md` 中标注「前台待补」）。
4. 截图证据落在仓库根目录 `.screenshots/<任务号>/`，文件名含 AC 编号。
5. **细颗粒度交付与断点**：
- **事前拦截**：AI 在写代码前必须先输出「修改计划（具体文件清单）」。如果单次新增/修改的文件数 **超过 5 个**，必须在开始前将其拆分为多个子任务。

- **事后断点**：如果写完后才发现文件超标或代码量过大，**严禁直接 `git checkout` 全部撤销**。应将已写完的代码作为一个独立 commit 保存，剩下未完成的部分拆为新任务继续执行，以节省 Token。

- **禁止混搭**：纯后端接口、纯前端组件、基础表结构与复杂业务关联，严禁在同一个 Task 内混合提交。
6. **严禁修改既有测试来“强行通过”**：如果是新代码导致老测试失败，必须分析是业务逻辑错了还是老测试真的过期了。如果是前者，**必须修代码**；如果是后者，**必须在回复中向用户显式说明原因，经用户同意后**才可修改测试期望值，严禁静默删除或改写既有用例。

## 4. Playwright 工程约定

### 4.1 工程结构与执行方式

- 工程位置：`D:\aitest_copilot\tests\e2e\`（pytest-playwright），不再另建 Node e2e 工程。

- **默认不随全量 pytest 执行**：`pyproject.toml` 的 `addopts` 为 `-m 'not e2e'`；前台用例统一打 `@pytest.mark.e2e`。

- 执行方式：常规直接用 `scripts/run_e2e.py`，它把起服务、自检、跑用例、收尾串成一步。

- 造数：`tests/e2e/support.py` 直连 e2e 库建用户，项目/成员/申请走真实 API；UI 只负责被验证的那一步。

### 4.2 用例命名与断言

- 用例命名 `test_ac_XX_<场景>_ui`，与 spec 的 AC 编号一一对应。

- 每个用例至少断言：页面可见文案 / 列表条数 / 关键按钮状态之一，不只看「没报错」。

- 失败自动截图 + 保留 trace；成功也保留 1 张关键帧（`shot` 夹具）。

- 登录态复用：`admin_storage_state` session 级 fixture 登录一次并复用 localStorage。

### 4.3 选择器与组件拆分约定

- **选择器约定**：前端新增/改动的交互元素统一带 `data-testid`（命名 `区域-动作-目标`，如 `tree-label-btn-12`、`snapshot-approve-btn`），e2e 优先 `get_by_test_id`。

- antd 内部类名（`.ant-tree-switcher_close`、`.ant-modal:visible`、`.ant-select-dropdown`）只作兜底，且必须限定在可见容器内——这些类名在升级后会变，T65 已在 `.ant-switcher_closed`、双弹窗 `.last` 上踩过。

- **组件拆分阈值**：单页组件超过约 400 行、或同时含 3 类以上弹窗/表格时拆子组件，避免一个文件里定位与回归成本过高。

- **组件职责隔离：** 如果同一个页面里既有“列表展示”又有“复杂表单/抽屉编辑”，必须强制拆分为两个独立组件（如 `XxxList.tsx` 和 `XxxDrawer.tsx`）。防止 AI 在一个文件里混合处理查询状态和表单状态导致级联渲染 Bug。

### 4.4 失败处理与回归

- **失败一次收齐**：一次跑完全部失败用例，集中读报错后批量修；修完先 `-k` 收窄验证，最后再跑一次全量。不要「改一行 → 重跑全量」逐条试，那是 T56–T65 耗时最大的原因。

- **增量修改与范围控制**：拆分或重构组件时，禁止擅自将未被本次任务覆盖的组件一并拆分（如 T65 拆分基线树时越界拆分快照页，已回退）。父组件超过 400 行时，优先拆分纯渲染子组件或常量，状态与事件编排尽量保留在主文件内。

### 4.5 AI 辅助开发提效约定

- **拒绝全量投喂**：对话开始时，禁止读取全量代码库。只允许 `@` 本次任务相关的核心文件。

- **先计划，后代码**：每个 Task 必须先输出「修改计划」，用户确认后再写代码。

- **局部验证优先**：写完代码后，先执行 `pytest -k ac_XX -n auto`，不要直接跑全量。

- **强制复用既有基建**：在编写任何新业务逻辑前，必须先在项目中搜索是否已有类似的工具类、服务层、权限函数或组件。禁止重复造轮子，所有数据库查询必须走当前项目已有的事务机制和查询封装。

- **复用 dev_check**：修改代码前先确认 `scripts/dev_check.py` 正常，防止环境假错导致 AI 盲目排查。

- **强制节点汇报**：当 AI 在执行包含多个文件或涉及多表操作的 Task 时，必须分步汇报。例如：先汇报“已完成模型与迁移”，等用户确认后，再汇报“已完成接口编写”。严禁一次性输出全套代码后才让用户验证。

**Tab 计数要限定顶层 tablist**（10 期 T122 实测踩到，11 期 T124 复核）：
antd 的两层 `Tabs` **都**用 `role="tab"`。进了「基线管理」之后，
`page.get_by_role("tab")` 会把内层的两个子 Tab 也数进去（10 + 2 = **12**）——
`test_tabs_ui.py` 原样通过是因为它**逐个点开**、只在进 Tab 之前计数。
本期要断言「顶层仍是 10 个」，写法是：

```python
top_tabs = page.get_by_role("tablist").first.get_by_role("tab")
expect(top_tabs).to_have_count(10)
```

`tablist` 在 DOM 里排第一（内层那个在顶层的内容区里），所以 `.first` 就是顶层。

> **11 期 T124 实测纠正**：只有**当前激活**的顶层 Tab 的内层子 Tab 会被计入——
> 已离开的顶层 Tab 面板是 `display:none`（`removeOnLeave` 默认 false，DOM 保留但不可见），
> 而 Playwright 默认 `include_hidden=False` 不计入隐藏元素。
> 所以顶层收敛为 8 个之后，裸计数是 **8 + 2 = 10**，**不是 12**。
> 结论不变：**断言顶层一律写 `get_by_role("tablist").first.get_by_role("tab")`**。

**antd v6 的 Select 值不在 `.ant-select-selection-item` 里**：
v6 换成了 `.ant-select-content-has-value`（单选）/ `.ant-select-content`（多选）。
断言「下拉已有值」要用 `expect(select.locator(".ant-select-content-has-value")).to_have_count(1)`，
用 08 期那条 `.ant-select-selection-item` 的写法会数到 0 条。

**antd Drawer 关闭后内容不销毁**：断言抽屉关掉了要用 `to_be_hidden()`，
**不是** `to_have_count(0)`（`destroyOnHidden` 没开时 DOM 里还在，只是隐藏）。
