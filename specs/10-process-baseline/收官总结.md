## 1. 结论摘要

10 期补齐了 PRD 2.4.2「基线管理」下的**第二个子菜单**——流程基线。
此前「基线管理」只有「功能基线」一个子菜单（模块 → 功能 → 功能点的三级树），
PRD 要求的「业务场景 / 前置条件 / 操作步骤 / 预期结果 / 关联功能基线」
**完全没有落位**。

本期把它做成了**与功能基线并列、但完全独立**的一套资产：

- **场景**（名称 / 描述 / 前置条件 / 来源 / 状态）；
- **操作步骤**（有序列表，整体覆盖，序号由服务端重排）；
- **关联功能基线**（M:N、无外键、名称快照）；
- **文档反推**（纯函数引擎，只出候选不写表）；
- **审核快照**（提交即冻结，通过转正）。

**本期最重要的三个设计裁决**（都不是「实现细节」，是会影响后续期的口径）：

| # | 裁决 | 为什么 |
|---|---|---|
| 1 | **独立建表，不复用功能基线的表** | 04 的 `baseline_labels.target_type` CHECK 写死两个层级名、`baseline_review_items.entity_type` CHECK 写死三个、`baseline_revisions` 的唯一键让两套基线**抢同一个版本号**。共用表会污染既有 CHECK、打断 04–09 的回归断言 |

## 3. 数据模型

### 3.1 四张新表（迁移 `0025`）

- **`process_baselines`**：场景名称、描述、前置条件、来源（`manual` / `document_derived`）、
  状态（`active` / `archived`）、`version_no`（**场景自身的修订次数**）、
  来源追溯 6 列。
- **`process_baseline_steps`**：一步操作 + 预期结果，`step_no` 由服务端按数组顺序重排。
- **`process_baseline_links`**：场景 ↔ 功能 / 功能点（M:N、单向）。
- **`process_baseline_revisions`**：审核记录 / 版本快照（**一体表**）。

**关键决策**：

- **`version_no` 在两处，含义不同**：`process_baselines.version_no` 是**场景自身的修订次数**
  （内容变更即 +1）；`process_baseline_revisions.version_no` 是**快照版本号**（`v1.{n}`）。
  PRD 的「版本号」同时出现在「流程基线字段清单」与「通用能力·版本快照」里，
  **是两个东西**，分别落位。
- **`process_baseline_links.target_id` 绝不建外键**：04 的删功能是**物理删除**，
  建 FK 会把 04 的既有行为变成 500（与 08 的 `test_point_id`、09 的 `linked_case_id`
  同一教训）。改用**逻辑引用 + `target_name` 名称快照**——
  目标被删后链接行仍在、名称可读、**04 的删除接口仍返回 204**。
- **`process_baseline_steps` 是 08 的 `test_case_steps` 的照抄**：同样的
  `ON DELETE CASCADE`、同样的列宽 1000、同样的「`step_no` 由服务端按数组顺序重排」。
- **快照表用两列而不是一列**（`draft_snapshot` + `structure_json`）：
  一列的话「提交时的内容」与「通过时的内容」会互相覆盖，驳回后就查不到当初提交的是什么。
  两列让「所见即所冻」成为**可断言的事实**。
- **来源追溯 6 列在 `source_type='manual'` 时强制置 NULL**：PRD 明确「手工添加」
  不做追溯要求。**服务端强制置 NULL，不采信客户端传值**。
- **`process_baseline_revisions.version_no` 可空**：驳回不占版本号
  （MySQL 唯一索引允许多个 NULL），审核中 / 已驳回的记录显示「待分配」。

### 3.2 迁移 `0025` 的另一半：模板 CHECK 扩枚举

`prompt_templates.task_type` 的 CHECK 从四个值扩到五个（多了 `'process_baseline'`），
并播种一条流程基线反推模板。

**为什么第 2 处不能省**（复用 `task_type='document_parse'` 会出事）：
复用会让 04 的推导下拉里同时出现「基线推导」与「流程基线推导」两个模板，
而 04 的服务端只校验 `task_type == 'document_parse'`
（`app/baselines/service.py:2416-2420`）——用户选了流程基线模板，
04 的解析器会拿到 `{"scenarios": [...]}`，**根结构校验失败，报错信息完全指不到真因**。

**`llm_run_logs.task_type` 为什么不动**：04 的文档推导**不写运行留痕**
（`run_document_derive` 里没有 `run_log.record_run`），本期的反推同构 → 不需要。

**`downgrade` 的三条顺序约束**（都是踩过坑的）：

1. **先扩 CHECK 再播种模板**——反了的话插入 `task_type='process_baseline'`
   的行会被旧 CHECK 拒（3819）；
2. **先删模板行再重建旧 CHECK**——残留的行会让旧 CHECK 重建失败（3819）；
3. **MySQL 不允许直接改 CHECK**，必须先 `drop_constraint` 再 `create_check_constraint`。

## 4. 架构与关键设计

### 4.1 反推引擎是纯函数（结构上做不到写表）

`run_derive(provider, template, document_name, version_no, chapters,
existing_scenarios, linkable_targets, max_chars)` 的签名里**根本没有 `session`**——
只要拿不到 Session，它就**不可能**写表。AC-202 断言「反推后三张表行数全部不变」，
这条断言之所以能成立，是因为**结构上就没有写表的路径**。

### 4.2 「已有清单」段要给两样东西（06 期 L2 联调翻车的教训）

Prompt 里拼两份清单：

1. **已有流程基线场景名清单**（防重复抽取）；
2. **可关联的功能基线清单**（模块 → 功能 → 功能点，**带 id**）。

**第二份不能省**：模型要产出关联就得知道有哪些目标可选、id 是多少。
06 期 L2 联调翻车就是因为没给清单——模型自己编 `target_id=1`，
编造的 id 全被当成越界丢弃，结论一条不剩。

引擎侧的容错也对应这点：**越界的 `target_id` 只丢那一条关联**，
候选与其步骤照常返回（04 没有关联概念，没有这条先例）。

### 4.3 步骤整体覆盖：先校验整组，再动手

`PUT /scenarios/{id}/steps` 的语义与 08 的 `PUT /cases/{id}/steps` **完全一致**：

- 校验不过 → **旧步骤原样保留**，一步都不改；
- 校验过了 → 先删旧、再按数组顺序插新，`step_no` 重排为 1..n；
- **客户端不发 `step_no`**——服务端不信模型 / 客户端给的序号。

**为什么整组拒**：半截状态（前三步是新写的、第四步是旧的）比「什么都没改」更糟——
用户以为改成功了，库里却是一份拼接物。

**空数组允许（清空关联）、但步骤的空数组不允许**：一个没有步骤的场景
**没有任何可执行内容**，是个残缺实体；一个没有关联的场景仍然是一个完整可用的
业务场景。两者语义不同，所以校验不同。

### 4.4 关联：单向 + M:N + 服务端重查名称

| 规则 | 值 |
|---|---|
| `target_type` | `function` / `feature_point` |
| 目标存在性 | 必须 `status='active'` 且 `project_id` 等于当前项目 |
| 名称快照 | 服务端**重查**目标名写入 `target_name`，**不采信客户端传值** |
| 重复关联 | 同一次提交里 `(target_type, target_id)` 重复 → 400 |
| 数量上限 | 单场景 ≤ 50 条 |

### 4.5 提交即冻结：审核人看到的与冻结的逐字节相同

```
提交审核 POST /reviews/submit  { comment? }
    3 当前无 active 场景 → 400 PROCESS_BASELINE_INVALID
    4 冻结：收集全部 active 场景 → draft_snapshot JSON + 三个计数

审核通过 POST /reviews/{id}/approve  { comment? }
    5 structure_json = draft_snapshot   ← **原样转正，逐字节相同**
    6 version_no = 项目内下一个 v1.{n}   ← **只查 process_baseline_revisions**

审核驳回 POST /reviews/{id}/reject  { comment }   ← **意见必填**
    3 不分配 version_no、不写 structure_json（draft_snapshot 保留供追溯）
```

**归档场景不参与快照**（与 04「归档模块及其功能不参与新快照」一致），
归档场景的步骤与关联也不计入计数。

**审核期锁定**：`update_scenario` / `delete_scenario` / `replace_steps` / `replace_links`
四个写入口都调 `_ensure_not_in_review`——**前端禁用只是体验，端上 409 才是保证**
（tasks.md §1 第 10 条）。

### 4.6 权限：校验顺序只有一处出处

**404（项目不存在）→ 409（归档）→ 403（角色）→ 400（业务）→ 执行**。

「归档先于角色判」这一条被 T121 **逐接口 × 逐角色**钉成了 3 条：
① 归档项目 + 项目管理员调 9 个写接口 → 全 409；
② 归档项目 + **普通成员**调 9 个写接口 → 全 409（**不是 403**）；
③ 归档项目 + 成员读 4 个读接口 → 全 200。

「项目不存在 → 404」覆盖读与写**各 13 个接口**；另有一条「404 优先于角色」——
非成员访问不存在的项目 → 404，不是 403。

### 4.7 前端的四条业务红线

1. **写入口只有项目管理员才渲染**：新建 / 反推 / 编辑 / 删除 / 关联 / 提交审核 /
   通过 / 驳回，成员与访客**一个都看不到**（不是「渲染了点了报 403」）。
2. **审核期锁定**：写入口禁用 + 提示「审核中，暂不可编辑」。
3. **反推候选默认全不勾**（PRD 1.4 原则二：高风险行为人工确认）。
4. **步骤顺序由服务端重排**——前端**不发 `step_no`**；
   **关联目标被删时标「目标已删除」但仍显示名称快照**。

### 4.8 二级子菜单：顶层 Tab 仍然是 10 个

PRD 2.4.2 明确流程基线是「基线管理」下的**并列子菜单**，
本期引入二级 `Tabs`（`defaultActiveKey="function"`）——
**现有用户路径不变**，进来还是先看到功能基线。

功能基线面板的渲染逻辑**一个字节都没改**（照搬原 `ProjectDetailPage.tsx` 里的
`<Space direction="vertical">` + `<Card title="功能基线结构">` +
`ProjectBaselineTree` + `ProjectBaselineSnapshots`），
e2e 的 `TAB_ANCHORS["基线管理"] = "baseline-keyword"` 依赖它。

## 5. 接口一览

前缀 `/api/projects/{project_id}/process-baselines`，13 个接口（10 条 path）：

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/scenarios` | 成员 | 场景列表（keyword / source_type / status 筛选，分页） |
| POST | `/scenarios` | 项目管理员 | **批量**新建（手工添加 / 反推候选采纳），**整批拒** |
| GET | `/scenarios/{id}` | 成员 | 详情（步骤 + 关联 + `target_deleted`） |
| PATCH | `/scenarios/{id}` | 项目管理员 | 改元数据（名称 / 描述 / 前置条件 / 状态） |
| DELETE | `/scenarios/{id}` | 项目管理员 | 删场景（**物理删除**，级联步骤与关联） |
| PUT | `/scenarios/{id}/steps` | 项目管理员 | **整体覆盖**步骤 |
| PUT | `/scenarios/{id}/links` | 项目管理员 | **整体覆盖**关联（**空数组合法**） |
| POST | `/derive` | 项目管理员 | 文档反推（**不写表**，返回候选 + 统计） |
| POST | `/reviews/submit` | 项目管理员 | 提交审核（**提交即冻结** `draft_snapshot`） |
| POST | `/reviews/{id}/approve` | 项目管理员 | 审核通过（`structure_json` 原样转正 + 版本号） |
| POST | `/reviews/{id}/reject` | 项目管理员 | 审核驳回（**意见必填**，不占版本号） |
| GET | `/revisions` | 成员 | 快照列表（状态筛选 + 分页） |
| GET | `/revisions/{id}` | 成员 | 快照详情（`draft_snapshot` / `structure_json` **原文**） |

校验顺序固定：**404 → 409（归档）→ 403（角色）→ 400（业务）→ 执行**。
任何一步失败**都不产生写入**（校验在建行之前）；**失败操作不写审计**。

**8 个错误码**：`PROCESS_BASELINE_NOT_FOUND` / `PROCESS_BASELINE_INVALID` /
`PROCESS_BASELINE_DUPLICATE_NAME` / `PROCESS_BASELINE_STEP_INVALID` /
`PROCESS_BASELINE_LINK_INVALID` / `PROCESS_BASELINE_REVISION_NOT_FOUND` /
`PROCESS_BASELINE_REVIEW_STATUS_INVALID` / `PROCESS_BASELINE_IN_REVIEW`。
另**复用 1 个既有的错误类**（不改 04 的判定逻辑，只复用类本身）：
`ReviewCommentRequired`（`REVIEW_COMMENT_REQUIRED`，400）——驳回意见必填。

## 9. 踩坑与修复

| 坑 | 处理 |
|---|---|
| **两套基线抢版本号** | 分表存储（§3.1）。AC-197 显式断言两套序列独立——同项目里功能基线发 `v1.0` 后，流程基线**仍发 `v1.0`** |
| **建 FK 让 04 的删功能变成 500** | `target_id` 不建外键 + 名称快照 + `target_deleted`；AC-200 断言 04 删除仍 204 |
| **模型瞎猜 `target_id`** | Prompt 给带 id 的功能基线清单；越界 id **只丢该条关联**；AC-202 断言 |
| **反推写出脏数据** | 引擎签名里没有 `session`；采纳走独立批量接口；AC-202 断言三表行数不变 |
| **批量采纳半批落库** | **整批拒**；AC-203 断言行数不变 |
| **步骤半截状态** | 先校验整组再动手；AC-199 断言旧步骤原样保留 |
| **自审开关的进程级缓存比事务回滚活得久** | `app/common/settings.py` 的 `get_setting` 缓存 60s；用例里 `set_setting(..., False)` 会把 False 一起缓存住，而**外层事务回滚只还原数据库、还原不了缓存**。修法：用例加 `autouse` 夹具，用完 `invalidate(...)` 掉那个 key；断言默认值时**直接读库**而不是走 `get_setting` |
| **造数不能靠被测账号** | 权限用例里被测账号的角色随时会变，靠它造数会自己把自己挡住。改成**另建一个项目管理员专供造数** |
| **9 个写接口不能顺序调用** | 「删场景」会把场景删掉，后面的接口只能撞 404；「审核通过」之后驳回是 409。改法：造数时建 **4 个场景**（改 / 删 / 覆盖步骤 / 覆盖关联各用一个），审核走「提交 → 通过 → 再提交 → 驳回」两轮 |
| **变量名也会被 grep 卡住** | 第一版用例里把变量命名为 `read_requests` / `write_requests`，被「零真实 socket」那条 grep 命中了——改成 `read_probes` / `write_probes` 才干净 |
| **antd 两层 `Tabs` 都用 `role="tab"`** | 进了「基线管理」后 `get_by_role("tab")` 会数到 **12**（10 + 2）——spec §8.1 说的「非活动面板懒渲染 → 内层未挂载」**只在没进 Tab 时成立**。断言顶层要写 `get_by_role("tablist").first.get_by_role("tab")` |
| **antd v6 的 Select 值不在 `.ant-select-selection-item` 里** | v6 换成了 `.ant-select-content-has-value`（单选）/ `.ant-select-content`（多选） |
| **antd Drawer 关闭后内容不销毁** | 断言「抽屉关掉了」要用 `to_be_hidden()`，**不是** `to_have_count(0)` |
| **`resetToServer` 写成 `useCallback` 会把 effect 的依赖带歪** | 它依赖 `scenario`，而 `scenario` 每次 `onUpdated` 都是**新对象**——列进 `useCallback` 的依赖后 effect 反复触发、步骤被反复重置。改法：保持成普通函数，effect 依赖显式写 `[open, scenario, form, isCreate]` |
| **保存后抽屉里的只读表必须跟着更新** | `onUpdated(updated)` 把新详情回传给父级；否则「上移第 2 步 → 保存」之后界面显示的还是旧顺序（库里已经是新顺序了） |
| **「新建」与「详情/编辑」两套表单会顶到 400 行** | 合并成同一个抽屉组件的 `mode` prop——同一个组件能覆盖的两种形态，就不要拆成两个 |
