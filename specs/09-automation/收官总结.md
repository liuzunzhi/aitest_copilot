## 3. 数据模型

### 3.1 三张新表（迁移 `0024`）

- **`automation_assets`**：文件名、**相对** `AUTOMATION_ROOT` 的路径、框架（pytest / playwright）、
  来源、解析置信度、识别到的用例数、`linked_case_id`（逻辑引用）、状态、在用 / 已归档。
- **`automation_runs`**：一次执行任务的记录——状态、退出码、统计（JSON）、日志、错误原因、起止时间。
- **`automation_run_items`**：这次执行里**每个资产**的结果 + 用例名称快照。

**关键决策**：

- **`file_path` 存相对路径，不存绝对路径**：绝对路径随部署环境漂移，且泄露服务器目录结构。
  绝对路径由服务端在执行时用 `AUTOMATION_ROOT` 拼出来。
- **`linked_case_id` 不建外键**：08 的删用例是**物理删除**，建 FK 会把 08 的既有行为变成 500
  （`IntegrityError`）。沿用 08 的 `test_point_id` 同一思路：逻辑引用 + `case_title` 快照。
- **`case_title` 快照**：用例被删后报告仍可读（`source_case_deleted=true`），
  且 **08 的删用例接口仍返回 204**。
- **`stats` 按资产维度**：与明细行数始终一致。pytest 的函数级计数只进 `log`——
  两套口径混在一张统计里用户会困惑。
- **明细粒度是「资产」不是「pytest 测试函数」**：一个文件里 N 个测试函数 → 一行明细，
  `result` 取汇总（有失败 → failed；全跳过 → skipped；否则 passed）。

### 3.2 迁移 `0024` 的另一半：清除原因枚举修正

| 旧值 | 新值 | PRD 2.4.2 |
|---|---|---|
| `priority_changed` | `baseline_adjusted` | 基线已调整 |
| `duplicate_label` | `backtrace_override` | 回溯覆盖 |

存量用两条 UPDATE 就地改写；`downgrade` **反向改回去**——
否则降级后代码只认旧枚举名，历史数据会被 04 的清除标签接口判成非法原因。

**枚举收敛到 `app/baselines/constants.py`**：`service.py` 与 `schemas.py`
原先各写一份，迟早漂移。**不能**让 `schemas.py` 反向 import `service.py`
（`service.py` 已 import `schemas.py`，会形成**循环导入**）——
所以常量放在无依赖的独立文件里。

## 4. 架构与关键设计

### 4.1 扫描是纯函数（结构上做不到写表）

`scan_dir` / `resolve_scan_dir` 的签名里**根本没有 `session`**——
只要拿不到 Session，它就**不可能**写表，「扫描不写表」这条 PRD 要求
就从「靠自觉」变成「结构上做不到」。

### 4.2 路径安全是红线（少判一条就是任意文件读取漏洞）

`resolve()` + `is_relative_to(root)` 双检挡住了 `../../etc`，
但挡不住 `C:\Windows`——Windows 上 `root / "C:\\Windows"` 会退化成
`root/C:\Windows`（仍在 root 内），`is_relative_to` 照样放行。
**绝对路径必须单独判。**

判定基准是 resolve 后的**实际路径**，不是字符串里有没有 `..`——
`sub/../sub2` 解析后仍在 root 内即放行。

### 4.3 入库时服务端重扫重算（前端不决定置信度）

前端传的置信度与用例数只是「扫描时的快照」。服务端入库时**重新扫描该文件**重算——
文件可能已被改动，更重要的是**不能让前端决定置信度**，
否则「随便写个 0.99」就能进库。

### 4.4 执行器三条安全线（缺一条就可能把后端拖死）

| # | 要求 | 实现 |
|---|---|---|
| 1 | **强制超时（默认 300s）** | `subprocess.run(..., timeout=timeout)`；没有超时的执行会让 HTTP 请求永久挂起 |
| 2 | **超时直接 kill** | 标准库在超时时已 kill + wait 回收；我们只捕获 `TimeoutExpired` 不让它冒泡 |
| 3 | **`communic()` 读输出** | `capture_output=True` 内部即 communicate；**禁止**「管道 + 阻塞式 `stdout.read()`」→ 死锁 |

第四条隐含红线：**不经 shell 解析**（参数以列表传入，`shell=False`），
文件名里的 `;` / `$` 不会变成命令注入。

### 4.5 状态语义靠 `error` 区分，不靠退出码

- `status='succeeded'` = pytest 进程**正常跑完**（**哪怕退出码是 1**——
  那只是「有测试失败」，是**业务结果**，不是系统错误）；
- `status='failed'` = 跑不起来（超时 / 启动失败），此时 `error` 非空。

实测：1 通过 + 1 失败 → `exit_code=1` / `status='succeeded'` / `error=None`；
超时 → `status='failed'` / `error` 含「超时」。

### 4.6 追溯链读快照，不联表（防 N+1）

08 已把 `test_point_name` / `target_name` / `chapter_title` 落库在用例行上，
报告直接读这些字段——**一次 `IN` 批量取**（N+1 的话几十条明细就是几十次往返）。

**这条有专门的回归断言**：`test_ac_191_report_query_uses_single_batch_load`
用 SQLAlchemy 事件钩子数 SELECT 条数——3 条明细时查用例表**必须恰好 1 次**。
比「代码里看着像一次 IN」可靠得多。

### 4.7 前端的四条业务红线

1. **写入口只有项目管理员才渲染**：扫描 / 入库 / 改关联 / 触发执行四个按钮，
   成员与访客**一个都看不到**（不是「渲染了点了报 403」——前端就不给入口）。
2. **Playwright 资产的执行按钮置灰** + tooltip「Playwright 执行能力待后续期」
   （本期只执行 Pytest：需要 node + 浏览器二进制，会引入浏览器网络请求）。
3. **状态文案分两套，绝不混用**：执行记录的状态说的是**执行进程**
   （`执行完成` / `执行失败`），明细的结果说的是**用例**（`通过` / `失败` / `跳过`）。
   文案取「执行完成」而不是「成功」，就是为了跟用例的「通过」区分开。
4. **追溯链四段齐全**：用例名称 / 测试点 / 目标 / 章节标题；
   `source_case_deleted=true` 时标「源用例已删除」。

## 5. 接口一览

前缀 `/api/projects/{project_id}/automation`，8 个接口：

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/scan` | 项目管理员 | 扫描目录，返回清单 + 置信度 + 统计（**不写表**） |
| GET | `/assets` | 成员 | 资产列表（框架 / 状态 / 关联用例筛选，分页） |
| POST | `/assets` | 项目管理员 | 人工确认批量入库（服务端重扫重算） |
| GET | `/assets/{id}` | 成员 | 资产详情 |

| POST | `/runs` | 项目管理员 | 触发执行（同步跑完返回） |
| GET | `/runs` | 成员 | 执行记录列表（**不带明细与日志**） |

`AUTOMATION_ASSET_NOT_FOUND` / `AUTOMATION_ASSET_INVALID` /
`AUTOMATION_FRAMEWORK_NOT_EXECUTABLE` / `AUTOMATION_RUN_NOT_FOUND` /

## 9. 踩坑与修复

| 坑 | 处理 |
|---|---|
| **平台自己的 pytest 配置会漏进被执行的资产** | `AUTOMATION_ROOT` 在仓库内 → pytest 向上找到平台 `pyproject.toml`（`addopts = "-q -m 'not e2e'"`）→ ①标了 e2e 的用例被**静默 deselect** ②`-q` 叠成 `-qq` → **统计行整个消失**。修法：按「资产有没有自己的配置」分流——有 → `-c <它>`，没有 → `-o addopts=` |
| **绝对路径挡不住** | `root / "C:\\Windows"` 在 Windows 上退化成 root 内拼接，`is_relative_to` 挡不住 → **单独判 `is_absolute()`** |
| **同名私有函数覆盖了 T112 的 `_cases_by_id`** | T114 写了同名的 `_cases_by_id(session, case_ids)` 收用例 id 集合，**静默覆盖**了 T112 那个收资产列表的 → 资产列表接口炸成 `ArgumentError`。修法：T114 改用 `_cases_by_ids`（复数）。**同名私有函数是最容易踩的隐形雷**——它不报错，只是把别人的行为换掉 |
| **全量 pytest 不能用 `-o addopts=`** | 平台的 `addopts` 含 `-m 'not e2e'`，覆盖掉它会把 56 条 e2e 一起收进来 → 它们要连 8001 端口 → 56 个 error。**要看用例数用 `-m "not e2e"`** |
| **Windows 上不能用 `os.kill(pid, 0)` 查进程存活** | 它会真的去终止进程。正确做法：`ctypes` 调 `OpenProcess` + `GetExitCodeProcess`，返回码 `259`（STILL_ACTIVE）才算活着 |
| **e2e 后端的 cwd 是仓库根** | `AUTOMATION_ROOT` 相对 cwd 解析 → 扫描扫的就是**仓库里的** `var/automation`。不往那儿写样例 pytest 文件，扫描永远返回空清单 |
| **`var/automation/` 不在 `.gitignore`** | e2e 造的样例文件会进版本库 → 已加进 `.gitignore`（用户放自己测试脚本的地方，不该进版本库） |
| **既有竞态：Select `disabled` 时点击是静默无效的** | 「模板」下拉选项异步加载，机器一慢就点空 → dropdown 永远不开 → 等选项超时。T115 加了会**真起 pytest 子进程**的用例后机器变慢，把这个**已存在**的竞态顶了出来。用 `git stash` 对照验证过（改动前 51 passed，改动后 55 passed + 1 failed）。修法：点之前先断言 `not_to_have_class(ant-select-disabled)` |
| **`disabled` 的按钮不派发鼠标事件** | antd 的 Tooltip 挂 disabled 按钮上永远不弹 → Tooltip 要挂外层 `<span>` |
| **MySQL CHECK 违约抛 3819 不是 1062** | 断言分开写（唯一索引才是 1062） |
| **e2e 库跑完会被清空** | 迁移往返脚本造标签需要 `baseline_revisions`（有外键）→ 库里没有就造最小前置数据，收尾一并删掉 |
| **造数也得照着真实的 CHECK 写** | `baseline_labels` 的必填列比想的多（`project_id` 不能省）；`baseline_revisions.status` 只认 `submitted` / `approved` / `rejected`——写 `draft` 被 MySQL 3819 拒了 |
